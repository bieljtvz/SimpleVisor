`ShvDirectMapBase` (used by the `PA_TO_VA` macro in [shvvmxhv.c](shvvmxhv.c)) used to be computed as a single global offset: allocate one `NonPagedPool` test page, get its PA/VA, store `VA - PA`, then apply that same offset to every physical address (guest CR3, page-table PFNs, etc.) during the manual GVA→HPA walk in `ShvTranslateVaWithCr3`.

This assumes the Windows direct physical map is one linear region covering all installed RAM. That only holds when physical memory is contiguous. On a machine with fragmented RAM (MMIO holes, memory above 4GB, hot-add ranges), the direct map is actually several separate VA regions. A PA outside the region sampled by the single test page produced a bogus host VA; dereferencing it inside `ShvTranslateVaWithCr3` (first dereference, walking `pml4e`) triggered a #PF. Since that happens inside the VM-exit handler with interrupts disabled, Windows deliberately bugchecks (`0xD1`, bucket `DISABLED_INTERRUPT_FAULT_shv!ShvTranslateVaWithCr3`) instead of trying to resolve the fault — a #PF with interrupts off is treated as fatal by design, not recoverable via `__try`/`__except`.

**Fix (applied 2026-10-11):** Replaced the single-offset scheme with a table of all physical memory ranges (`ShvPaRanges[]` / `ShvPaRangeCount` / `SHV_PA_RANGE`, declared in [shv.h](shv.h), defined in [shvvmxhv.c](shvvmxhv.c)). [nt/shvos.c](nt/shvos.c) builds it once at `PASSIVE_LEVEL` before `ShvLoad()`, via `MmGetPhysicalMemoryRanges()` + `MmGetVirtualForPhysical()` per range. `ShvPaToVaSafe()` in shvvmxhv.c does a pure array lookup (no kernel calls, safe with interrupts disabled) and returns 0 for any PA not covered by a known range. `ShvTranslateVaWithCr3` now checks this 0 at every paging level (PML4/PDPT/PD/PT) and aborts the translation instead of dereferencing a possibly-invalid host VA. `ShvReadVaWithCr3`/`ShvWriteGuestVa`/`ShvSyscallDispatch` also check `PA_TO_VA()`'s result for 0 before dereferencing.

**Why:** Correctness of guest-memory access from VMX root mode depends on never dereferencing a host VA that might not be backed by resident memory — a single test-page offset is a lucky guess, not a guarantee.

**How to apply:** Any new code that needs PA→HVA translation in VMX root mode (e.g. new EPT/syscall-hook logic) must go through `ShvPaToVaSafe()`, not a raw offset add, and must check for a 0 return before dereferencing. Related: [[feedback_manual_mapping_cr3]] (another VMX-root CR3/paging footgun in the same file).

**Update 2026-10-11 (same bugcheck recurred after the fix above, via the `ShvSystemCr3` path in `ShvVmxHandleException`'s SYSRET-detection read, not `GUEST_CR3`):** the range-table lookup itself can still produce a non-kernel-looking VA (observed: `0x0000030A98C35F80`, clearly not a canonical kernel address) for reasons not yet root-caused — possibly a bad/overlapping entry in `ShvPaRanges[]`. Added a second, independent guard in `ShvPaToVaSafe()`: reject (return 0) any computed VA below `0xFFFF800000000000` (the x64 kernel-space floor), regardless of why the table produced it. Tracked with `ShvPaToVaRejectCount` / `ShvPaToVaLastBadResult` (readable in WinDbg: `dq shv!ShvPaToVaRejectCount`, `dq shv!ShvPaToVaLastBadResult`, and `dd shv!ShvPaRangeCount` / `dx shv!ShvPaRanges,10` to inspect the table itself) — check these after a crash/break to see whether the table was built correctly and how often the guard is firing, since that's the next real diagnostic step if the bugcheck recurs again.

**Update 2026-10-11 #2 (new crash, same session, after the guard above started working — confirmed via `ShvPaToVaRejectCount` > 0 in WinDbg):** the hypervisor itself stopped bugchecking on the bad translation, but that exposed a *different*, worse bug: when `ShvReadVaWithCr3(VpState->GuestRip, ..., ShvSystemCr3)` in `ShvVmxHandleException`'s `cpl == 0` branch now correctly fails (returns 0) instead of faulting, the old code treated "read failed" exactly like "confirmed not a SYSRET" and re-injected `#UD` into the guest. Since `EFER.SCE=0` is set system-wide, almost every `cpl==0` `#UD` *is* a genuine SYSRET (every kernel→user return goes through `KiKernelSysretExit`); re-injecting a bogus `#UD` into a real SYSRET corrupted the real OS's execution and cascaded into a stack-overflow page-fault storm → double fault → bugcheck `0x7f` (`UNEXPECTED_KERNEL_MODE_TRAP`), observed on a WOW64 process (`AnyDesk.exe` → `wow64cpu!BTCpuSimulate` → `nt!KiKernelSysretExit`). **First attempted fix (wrong, made things worse):** only re-inject `#UD` when the byte-read *succeeded* AND confirmed the opcode isn't `0F 07` (SYSRET); on read failure, fall through and *assume* SYSRET and emulate it. This traded a debuggable bugcheck for something worse: a **silent freeze with no bugcheck at all** (all CPUs hang, WinDbg can't even break in — the same failure mode documented in [[feedback_manual_mapping_cr3]]). Root cause: not every `cpl==0` `#UD` is actually a SYSRET (there can be genuine `UD2`/illegal-instruction traps elsewhere in the kernel); blindly emulating SYSRET over one of those corrupts `RIP`/`RFLAGS`/`CS`/`SS` with garbage from `RCX`/`R11`, producing invalid guest state that the CPU/VMX can't recover from cleanly — worse than a bugcheck, because there's no diagnostic trail.

**Fix #3 (2026-10-11):** stopped guessing in either direction. Realized `ShvSystemCr3` was never the only — or even the best — CR3 to read `VpState->GuestRip` through: by the time this `#UD` fires, the **hardware already fetched and decoded** the faulting instruction at `GuestRip` using the *current* `GUEST_CR3`, so a software walk of `GUEST_CR3` for that exact GVA is guaranteed to succeed (the KVA-shadow trampoline containing the real `SYSRET` is deliberately mapped into the shadow/user CR3 too, precisely so the CPU can fetch it after the CR3 switch but before the actual ring transition). So the read now goes `ShvReadGuestVa()` (via `GUEST_CR3`) first, falls back to `ShvSystemCr3` only if that somehow fails, and — critically — reverted the failure-fallback to the original, safe direction: if neither translation succeeds, **re-inject `#UD`** (debuggable bugcheck) rather than assume SYSRET (silent unrecoverable freeze). General lesson: (1) a translation-failure fallback must never silently assume the "convenient"/common case when picking wrong corrupts live CPU state — fail toward the outcome that stays diagnosable; (2) when you need to read bytes at the *current* faulting RIP specifically, translate through the CR3 that was actually active when the fault happened, not a cached/alternate one — the hardware's own successful fetch is the strongest guarantee you can get.

**Fix #4 (2026-10-11, same day, after migrating syscall monitoring to the EPT-hook path — see [[project_ept_hook_over_efer_sce]]):** the *same* bugcheck `0xD1`/`DISABLED_INTERRUPT_FAULT_shv!ShvTranslateVaWithCr3` recurred a 4th time, now via `ShvSyscallDispatch` → `ShvTranslateGuestVa` → `ShvTranslateVaWithCr3`, translating `GUEST_CR3` (not `ShvSystemCr3`) while reading the `CLIENT_ID` argument (`R9`) of `NtOpenProcess`. This was the decisive clue: `GUEST_CR3` is, by definition, the CR3 the CPU is *actively using right now* on this logical processor — unambiguously a valid, resident physical page. If translating that fails, the bug can't be a transient race; it has to be that `ShvPaRanges` itself doesn't cover that PA. Root cause: `ShvPaRanges` is a **snapshot taken once in `DriverEntry`** via `MmGetPhysicalMemoryRanges()`. If the system's physical memory map changes afterward (hot-add, a VM's dynamic/balloon memory — plausible given `WER.OS.Branch: vb_release` pointing at a virtualized test box), the snapshot goes stale: a PA outside its original coverage can, by coincidence, fall inside an old entry's numeric bounds and produce a VA that still passes the `SHV_KERNEL_VA_MIN` canonical-floor guard (looks like a real kernel VA) while being the wrong translation.

**Actual fix:** stopped trusting any precomputed snapshot. `ShvPaToVaSafe()` now calls a new OS-provided function, `ShvOsPaToVa()` ([nt/shvos.c](nt/shvos.c)), which calls `MmGetVirtualForPhysical()` **directly, fresh, every single translation** — no snapshot, so no staleness is possible. `MmGetVirtualForPhysical` is documented as callable at any IRQL (it's a non-blocking PFN-database lookup), which is why it's safe to call from inside the VM-exit handler with interrupts disabled — same category of reasoning that already justified `ShvReadGuestReturnAddress`'s direct kernel-VA dereference. The `SHV_KERNEL_VA_MIN` canonical-floor check is kept as a last line of defense on top of this. `ShvPaRanges`/`ShvPaRangeCount` are left in place (built, but no longer consulted) purely for diagnostics. General lesson: a cached snapshot of "the physical memory map" is a liveness assumption — don't build one for something you'll use at an unpredictable future time unless you can guarantee it never goes stale (or refresh it); prefer asking the OS's own live, authoritative answer when a safe way to do so exists, even from a constrained context like VMX root.

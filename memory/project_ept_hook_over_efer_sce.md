SimpleVisor had two parallel mechanisms for observing syscalls:

1. **EFER.SCE=0 + `#UD` interception** ([shvvmx.c](shvvmx.c) VM-launch setup, handler `ShvVmxHandleException` in [shvvmxhv.c](shvvmxhv.c)): cleared `EFER.SCE` in `GUEST_EFER` and intercepted vector 6 (`#UD`) system-wide, so *every* `SYSCALL`/`SYSRET` in the whole OS faulted into the hypervisor, which had to manually decode/emulate them (read opcode bytes to distinguish real `SYSRET` from `UD2`, rebuild `RIP`/`CS`/`SS`/`RFLAGS` by hand).
2. **EPT execute hook** (`ShvHookInstall`/`ShvHookTable` + `ShvVmxHandleEptViolation` + MTF re-arm, in [shvvmxhv.c](shvvmxhv.c)): marks a physical page non-executable in EPT; a VM-exit fires only when the CPU fetches from that exact page, with no ambiguity and no need to read/emulate anything.

**Decision (2026-10-11): mechanism 1 is disabled.** It caused a chain of real crashes during testing — bugcheck `0xD1` (dereferencing a bad direct-map VA built from a wrong single-offset assumption), bugcheck `0x7F` double fault (re-injecting a bogus `#UD` into a genuine SYSRET), and a silent triple-fault freeze (blindly assuming SYSRET on a translation failure). Root issue: this design requires correctly emulating *every* `SYSCALL`/`SYSRET` on the entire system, including disambiguating it from `UD2` by reading guest memory from VMX root under hostile conditions (interrupts disabled, KPTI shadow-CR3 ambiguity, no locks) — any mistake corrupts kernel execution OS-wide. The project's own comment in shvvmxhv.c (now also noted at the disable site) already said the correct next step was an EPT hook, before this was actually done.

**What was changed:**
- [shvvmx.c](shvvmx.c) (`ShvVmxLaunchOnVp`): `EXCEPTION_BITMAP` set to `0` (was `1UL << EXCEPTION_VECTOR_UD`); `GUEST_EFER` now written as the real host `EFER` value (was `& ~EFER_SCE`). Guest `SYSCALL`/`SYSRET` now execute natively with zero VM-exit overhead.
- [shvvmxhv.c](shvvmxhv.c) `ShvVmxHandleException`: left in place as reference/study code (how the emulation worked) but is now unreachable in practice — it's still called for `EXIT_REASON_EXCEPTION_NMI`, but only a genuine NMI can trigger that now, never a `#UD` from `SYSCALL`/`SYSRET`.

**Current state of the EPT path (reviewed same day):** the *generic* hook table (`ShvHookTable`, armed via the usermode tool's `hooke` command → `SHV_IOCTL`, landing in `ShvHookInstall`) is live and working — it supports READ/WRITE/EXEC hooks with shadow-page swap and MTF re-arm, and is how you'd put an EXEC hook on `KiSystemCall64` today. There is also a vestigial "legacy" single-hook slot, `ShvEptHookPhysical` (declared in [shv.h](shv.h), checked in `ShvVmxHandleEptViolation`/`ShvVmxEptRearmHook`) — **this is dead code**: nothing in the codebase ever assigns it (grep confirms the only write is its own `= 0` initializer), so that specific "legacy KiSystemCall64 hook" path and its `ShvEptHookHitCount`/"EPT Exec Hits (KiSystemCall64)" UI counter never fire. Not removed (out of scope of this change), just noted as unused.

**Known gap to fix before the EPT hook is actually useful for syscall monitoring:** when an EXEC violation fires on `KiSystemCall64`, `ShvVmxHandleEptViolation` currently logs only `(guestRip, retAddr, guestPa)` via `ShvHvPushEvent` — it does **not** capture `VpState->VpRegs->Rax` (the syscall number) or the argument registers (`Rcx`/`Rdx`/`R8`/`R9`), even though they're already in the right registers per the `SYSCALL` calling convention at that exact point (no page walk needed, unlike the old approach). Add that capture (likely needs a wider event struct, or a dedicated event type) before relying on this hook for actual syscall monitoring.

**How to apply:** don't re-enable the EFER.SCE/`#UD` path for syscall monitoring. Extend the EPT exec-hook path instead — arm it on `KiSystemCall64`'s physical address via the existing `ShvHookInstall(..., SHV_HOOK_EXEC, ...)` flow, and extend the EPT-exec event logging to include `Rax`/args. Related: [[feedback_direct_map_single_offset_bugcheck]] (the three bugs that motivated this decision).

**Update 2026-10-11 (implemented): PID protection ported to the EPT path.** Added `ShvSyscallHookVa`/`ShvSyscallHookHitCount`/`ShvSyscallHookBlockCount` (declared [shv.h](shv.h), defined [shvvmxhv.c](shvvmxhv.c)). [nt/shvos.c](nt/shvos.c) `DriverEntry` reads `__readmsr(MSR_LSTAR)` (still untouched by anything at that point) right before `ShvLoad`, resolves it to a physical address with `MmGetPhysicalAddress`, stores the VA in `ShvSyscallHookVa`, and arms it via the existing `ShvHookInstall(pa, SHV_HOOK_EXEC, 0, 0)` — reusing the generic hook table, not the dead `ShvEptHookPhysical` slot. After `ShvLoad` succeeds, calls `ShvFlushHooksAllCpus()` once (same pattern every other hook-install IOCTL path already uses) so the EPT permission actually gets applied on all CPUs immediately instead of waiting for each CPU's next organic VM-exit.

In `ShvVmxHandleEptViolation` ([shvvmxhv.c](shvvmxhv.c)), added a check for the EXACT entry (`guestRip == ShvSyscallHookVa`, not just "same physical page" — the generic per-page logic stays untouched and still logs every EXEC violation on that page, including the ones from the MTF single-step window after the real syscall is allowed through). On that exact hit, calls `ShvSyscallDispatch` (unchanged — it already read `VpRegs` directly, so it needed zero changes to work from this new call site; `R10`/`RDX`/`R8`/`R9` already hold the syscall args per the `SYSCALL` calling convention regardless of which mechanism intercepts). If it blocks: reconstructs a "return to caller" by hand — `GUEST_RIP = RCX`, `GUEST_RFLAGS` from `R11`, `CS`/`SS` from `STAR`, `RAX = STATUS_ACCESS_DENIED` — reusing the exact math from the old (now-dead) SYSRET emulation, which is valid here because at this exact point (before `KiSystemCall64` has executed a single instruction) `RCX`/`R11` still hold exactly what hardware `SYSCALL` put there (original user `RIP`/`RFLAGS`), identical to what the kernel's own exit path would have used for a real `SYSRET`. If allowed: falls through to the existing generic "restore X=1 for 1 instruction + MTF re-arm" flow unchanged, so the real `Nt*` routine runs normally.

**Update 2026-10-11 #2: the `ShvSyscallHookVa` EPT-exec hook caused a severe system-wide slowdown in testing** (52M+ `EPT Execute` events from a handful of processes in minutes, confirmed via the events console showing consecutive RIPs single-stepping through `KiSystemCall64`). Root cause: the generic observe-hook flow restores `X=1` for exactly 1 instruction then re-blocks (`X=0`) the *whole 4KB page* via MTF — since EPT has no sub-page granularity, and `KiSystemCall64`'s dispatcher body spans many instructions in that same page, **every single instruction of the hottest function in the kernel re-triggers a full VM-exit**. This mechanism is fine for a rarely-hit function; catastrophic for the universal syscall entry point. `unhook all` in the events console is the immediate recovery if this happens again.

**Decision: abandoned the EPT-exec hook on `KiSystemCall64` for PID protection entirely** (the mechanism/globals stay in the code, just no longer auto-armed at `DriverEntry`, available for manual study via IOCTL). Replaced with an **inline trampoline hook on `NtOpenProcess` itself** (not `KiSystemCall64`) — see [[feedback_direct_map_single_offset_bugcheck]] for why patching a hot function needed this redesign, and the new `HpvHookFuncByVa`/`HpvHookFuncByName`/`HpvUnhookFuncByVa` multi-hook-safe-sharing fix (same file, same day) for the mechanism this relies on. Why `NtOpenProcess` is a safer patch point than `KiSystemCall64`'s raw entry: by the time `NtOpenProcess` is called (via a normal `CALL` from the syscall dispatcher), the kernel stack/GS base/trap frame are already fully set up — patching the very first instructions of `KiSystemCall64`/`KiSystemCall64Shadow` itself risked executing hook code *before* the KVA-shadow CR3 switch and kernel-stack switch complete, i.e. doing stack operations against a possibly-still-user RSP.

**`HpvOpenProcessHook`** ([nt/shvos.c](nt/shvos.c)) is a normal C function with `NtOpenProcess`'s exact signature, installed via `HpvHookFuncByName(L"NtOpenProcess", HpvOpenProcessHook, &g_OriginalNtOpenProcess)` right after `ShvLoad()` succeeds. Checks `ClientId->UniqueProcess` against `ShvHookProtectedPids` (same array `ShvSyscallDispatch` in the hypervisor reads) and returns `STATUS_ACCESS_DENIED` without calling through if protected; otherwise tail-calls `g_OriginalNtOpenProcess` (the trampoline: displaced original instructions + `JMP` back). Key win over every previous attempt: `ClientId` arrives as an ordinary C pointer argument — no manual CR3 walk, no `ShvPaToVaSafe`, and `__try`/`__except` around `ProbeForRead(ClientId, ...)` **actually works** here, because this runs in normal kernel-mode context (not VMX root with interrupts disabled), so a bad user pointer raises a real, catchable exception instead of a bugcheck. This eliminates the entire bug class chased all session for *this* read. Deliberately minimal for this first test (no trusted-caller allowlist, matching what `ShvSyscallDispatch` already didn't have either) — add that layer later if needed.

**IPI-based IEP (temporarily freezing other CPUs before patching a shadow page already live/shared by another hook) was explicitly deferred by the user** — "não implemente o IPI ainda, vamos testar somente com o NtOpenProcess atual". Noted as a residual risk, not yet mitigated: see the multi-hook-sharing fix note above.

**Update 2026-10-11 #3: shadow page never actually hid the patch from reads — found by the user testing.** The shadow-page EPT mechanism ([shvvmxhv.c](shvvmxhv.c): `ShvVmxEptApplyHooks`, `ShvVmxEptRearmHook`, `ShvVmxHandleEptViolation`) always mapped the shadow with `R=1,W=0,X=1`. That means *reads* were served directly from the shadow (patched) page, same as execution — the `JMP` stub was fully visible to anyone just reading the function's bytes (an integrity check, a disassembler, a debugger). `W=0` only ever caught *writes*; `ShvEptExecuteOnlySupported` was checked (gating the whole mechanism on it) but never actually used — `R` was hardcoded to `1` in all three call sites, so true execute-only (`R=0,X=1`) was never configured despite the capability check implying that was the intent.

**Fix:** changed the steady state to `R=0,W=0,X=1` (true execute-only) in both `ShvVmxEptApplyHooks` and `ShvVmxEptRearmHook`. Since any read now legitimately violates, `ShvVmxHandleEptViolation`'s shadow-page block now branches on `exitQual`: a **read** violation (bit 0x1) remaps the GPA to the **original** identity PFN (`GuestPhysical == HostPhysical == page`, already an established pattern elsewhere in the same file) with `R=1,W=0,X=0` for exactly one instruction — so the reader sees genuinely unmodified bytes — while a **write** violation (bit 0x2) keeps the original behavior (opens the *shadow* for write). Either way, MTF then restores `R=0,W=0,X=1` on the shadow. Net effect: execution is always from the patched copy (zero overhead, as before); any read sees the true original bytes; any write still only touches the shadow copy. This is the real "hide the patch from inspection" property the execute-only capability check always implied but never delivered.

**Update 2026-10-11 #4: second simultaneous hook added for multi-hook test, per user request.** `HpvReadVirtualMemoryHook` ([nt/shvos.c](nt/shvos.c), right after `HpvOpenProcessHook`) — deliberately minimal (increments `ShvReadVirtualMemoryHookHitCount`, never blocks, always calls through `g_OriginalNtReadVirtualMemory`), installed via the same `HpvHookFuncByName` right after the `NtOpenProcess` install in `DriverEntry`. Purpose: exercise the multi-hook-safe-sharing fix (RefCount'd shadow pages, overlap check) with a second real hook, specifically to see whether `NtOpenProcess` and `NtReadVirtualMemory` land on the same or different physical 4KB page — `HpvHookFuncByVa`'s own debug log (`reusedShadow=%u`) and `SHV_CMD_LIST_SYSCALL_HOOKS`'s `FuncGpa` field both show this directly, no extra plumbing needed. `dq shv!ShvReadVirtualMemoryHookHitCount` in WinDbg confirms the second hook fires independently of the first.

**Update 2026-10-12: `HpvShadowPatchAddress` added, then both hook paths refactored onto one shared primitive (user caught a real duplication risk).** First added `HpvShadowPatchAddress(Buffer, Address, Size)` — a lower-level "raw shadow patch" primitive, no trampoline/no disassembly, for short in-place patches (vs. `HpvHookFuncByVa`'s full function-redirect hook). It initially had its own **copy** of the same-page-sharing logic (find-or-create shadow, overlap check, RefCount) — a second, independent implementation of the exact same correctness-critical logic already in `HpvHookFuncByVa`. User flagged this directly: the same-page correction needs to live in one place, not be reimplemented per call site where only `HpvHookFuncByName`'s underlying `HpvHookFuncByVa` was kept correct while others could drift.

**Fix:** extracted three shared primitives (`HpvShadowPageAcquire` / `HpvShadowPageCommit` / `HpvShadowPageAbort`, all in [nt/shvos.c](nt/shvos.c) right before `HpvHookFuncByVa`) and rewrote **both** `HpvHookFuncByVa` and `HpvShadowPatchAddress` to go through them — neither has its own copy of the shadow-creation/reuse/overlap logic anymore. Protocol: `Acquire(Address)` finds-or-creates the page's shadow and returns a VA safe to *read* from (no overlap check yet, since `HpvHookFuncByVa` doesn't know its own patch size until it disassembles from that VA); once the caller knows the exact patch size, `Commit(FuncPage, FuncOffset, PatchSize, ...)` checks overlap against every other entry on that page and only then bumps `RefCount` — only after `Commit` succeeds does the caller write the actual patch bytes; `Abort(...)` undoes a freshly-*created* shadow (no-op for a reused one, since reuse doesn't mutate anything until `Commit`) if the caller bails between `Acquire` and `Commit` for any reason (disassembly failure, table full, etc.). General lesson: when a safety invariant (here: never let two patches on the same physical page corrupt each other) has more than one call site, it must be centralized in one primitive both paths are *structurally forced* through — a correctness fix applied to only one copy is a trap for the next feature added the same way.
